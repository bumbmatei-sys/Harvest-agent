# Community membership, chunks (a) and (b)

The join/leave APIs support membership in many communities without moving
`users/{uid}.tenantId` or changing Auth claims. No URL or membership depends on a
subdomain. Community content now uses active membership, independently of the account tenant.
The existing community list consumes the reverse index; UI redesign remains chunk (d).

## Records

`tenants/{tenantId}/communityMembers/{uid}` retains `rulesAcceptedVersion`,
`answers` (a question-id to string map), and `answeredAt`. New joins also write
`uid`, `tenantId`, `status` (`active` or `left`), `source` (`discover`, `link`, or
`website`), `joinedAt`, `leftAt`, `consentAt`, and `updatedAt`. All timestamps are
Firestore Admin SDK Timestamps generated by the server. An active membership has
`leftAt: null`. Leaving retains the record and all its onboarding/history fields;
rejoining replaces the join/source/consent timestamps and clears `leftAt`.

The server-only reverse index is `users/{uid}/memberships/{tenantId}` with
`tenantId`, `status`, `joinedAt`, and `leftAt`. Both records change in one
transaction, with deterministic document IDs. Clients can list their own index
without collection-group queries or composite indexes. No profile information is
duplicated into either record.

An explicit status always wins. Without status (including no entry document),
legacy membership requires the actual `users/{uid}.tenantId` to match; a token
claim or an unrelated onboarding document is insufficient. Active legacy joins
remain no-ops, so they do not backfill the reverse index. The client combines
the index with the legacy primary tenant and rechecks member documents until a separate backfill is authorised.
Leaving such a legacy member creates an explicit `left` marker; the index uses
`joinedAt: null` when no historical timestamp exists, and no consent is fabricated.

## Endpoints

- `POST /api/community/join`: Firebase ID-token authentication through
  `requireAuth`; JSON `{ tenantId, source, consent: true,
  rulesAcceptedVersion?, answers? }`. Requires a tenant, public community settings,
  and a published discovery listing. An explicitly non-active tenant cannot be
  joined. This uses the existing publication condition, `settings.isPublic`, and
  rechecks it transactionally to reject stale listings. Private/unlisted
  communities are rejected for every source, including a direct link. There is
  no separate community-enabled flag in the current schema.
- An already active membership returns 200 without changing records. New/rejoin
  requests must accept the current rules when enabled and supply required
  onboarding answers when enabled. Omitted onboarding fields retain prior values;
  a new member without answers retains the legal `communityQuestionsPending` answer marker
  so the old entry flow can ask questions enabled later.
- `POST /api/community/leave`: JSON `{ tenantId }`. Marks active memberships left;
  an absent/already-left membership returns 200 without writes. Owners, scoped
  user-doc/token admins, and private-roster admins cannot leave their tenant (400).
  Leaving remains possible after a community becomes private or is suspended.
- Successful responses are `{ ok: true }`. Invalid JSON, IDs, payload fields,
  sources, consent, or onboarding return 400; unauthenticated callers get 401;
  non-joinable communities get 403; missing tenants get 404. Failed reads/writes
  and malformed saved settings/rosters return a visible 503 JSON error.

Tenant IDs accept 1–128 ASCII letters, digits, underscores and hyphens, starting
with a letter or digit. Answers are bounded to 100 string entries, 128-character
keys, and 4,000-character values. Unknown top-level fields are rejected. The
neighbouring community routes do not use rate limiting; these follow that pattern.
Neither handler logs tokens, profile emails, or payloads.

## CRM integration point

`upsertCommunityContact({ uid, tenantId })` in `src/lib/community-contact.ts` is an
intentional no-op for chunk (c). The join handler awaits it after committing the
membership transaction and also invokes it for active retries. Chunk (c) must
implement an idempotent upsert and let failures propagate; retrying a join can
then repair a failed contact write without rewriting membership timestamps. No
contact is created in chunk (a), and leave does not remove any contact.

## Rules boundary

Only the server may create or change membership identity, status, source, or
membership timestamps. The old onboarding flow may create its original three
fields only for a genuine legacy member, or merge changes to those fields for an
active member. Full replacements that remove server fields and all client deletes
are denied. The existing save hook uses `mergeFields` for the three onboarding
fields, preserving server metadata while replacing the entire answers map so a
completed submission clears the pending-questions marker.

Users may read their own member document, including after leaving. Scoped admins
and owners may get/list their tenant's member documents; unrelated members and
foreign tenant admins are denied. The per-user index permits only self get/list
and no client writes, including admin writes.

`isActiveCommunityMember(tenantId)` gates community member operations: posts,
comments, reactions/RSVPs, the communal prayer wall, channels/messages, DMs,
community settings/reviews and livestream chat reads. Existing staff moderation
and platform grants remain independent. An explicit leave overrides legacy
membership and stale token claims. Author-only delete paths also require active
membership. The server's `requireCommunityMember` and transactional review recheck
use `community-membership-server.ts`, which delegates to `isActiveMember`.

The community admin directory/count unions primary users and active member docs,
deduplicates and excludes explicit leaves. Its existing settings endpoint exposes
only directory fields, with foreign staff roles mapped to member. Full user docs,
CRM, finance, billing, course material, service plans and event registrations keep
their old tenant/role checks. Public events retain their existing authenticated
read policy; there is no separate community event collection. New membership
alone confers no staff or money authority.

TenantContext continues selecting the host tenant independently of the account's
primary tenant. Existing community links therefore open joined communities without
rewriting user data or claims. The Free shell lists joined communities too; its owned Free personal workspace
without a subdomain is not a community card. Both
pending-marker spellings are read; all writes use the legal spelling, and question
submission removes both. The join API rejects reserved answer field names.

`firestore.rules` auto-deploys on merge. Founder approval is still required before
merging/shipping these exact rules changes; no deployment is part of this work.
